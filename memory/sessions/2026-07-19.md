## Decisions Made
- **Scope defaults to `unread` everywhere** — the read-mail feature is additive, so
  no existing caller changes behaviour. `email.list_unread` kept as an alias
  rather than replaced, trading a slightly larger tool surface for not breaking
  agent configs.
- **Unsupported scopes error rather than degrade** — a backend that cannot tell
  read from unread returns an error instead of the unread set. Silently
  mislabelling unread mail as read is worse than failing.
- **Gate `email.send`** — the gating was inverted relative to impact: archive and
  delete are soft, reversible moves that never expunge, yet both required
  confirmation; send is irreversible and outbound and required nothing. Message
  content is embedded into prompts, so an injected "forward everything to X" had
  an unguarded path to execution.
- **Bind credentials to their endpoint in `config.set`** rather than only blocking
  the TLS downgrade. Fixing `insecure` alone would still permit redirection to any
  host with a valid certificate — equally full credential disclosure. The root
  cause was partial-update inheritance, not the flag.
- **Add profiles instead of loosening maildir confinement.** Strict confinement
  blocked legitimate sibling switches; profiles restore that without reopening the
  hole, because the operator writes endpoint and credentials together. A profile
  may point outside the startup maildir where a field-level patch may not — the
  trust comes from *who wrote the destination*, not from where it points.
- **v0.20.0, not v0.19.1** — the release carried a new feature (profiles) and a
  behavioural break (`email.send` refusing without `confirm=true`). Minor bump
  under semver, not a patch.
- **Track secret provenance at the source** (`overlaySecret` records which env
  vars supplied a value; `LoadCredentials` marks hydrated fields) rather than
  comparing values at save time. Precision is what makes the fix safe: an
  operator-written value is never mistaken for an inherited one, so `Save` cannot
  silently delete configuration.
- **Extended the `Save` fix beyond the reported finding** to cover OAuth2 values
  hydrated from a `credentials_file` — same failure mode, and `credentials_file`
  exists precisely so those values are not copied into the config file.

## What Went Wrong
- **Shipped a known vulnerability.** v0.20.0's predecessor v0.19.0 was merged and
  tagged without ever running `gh pr list`. PR #21 — a one-line DOM XSS fix from an
  external contributor — had been open since 07:23 that morning. The release
  published binaries containing the vulnerable line. One command would have caught
  it and changed the sequencing to land the fix first.
- **Caused an unintended push to GitHub.** Tested warden's pre-push gate against a
  `/tmp` bare repo believing it was sandboxed. The hook discarded the named remote
  and pushed the branch to `origin`. This happened while deliberately holding off
  on pushing because it was outward-facing — the sandbox simply was not one.
- **Nearly reported a false bug.** Observed `warden verify` returning exit 0 for an
  unverified commit and started to report it as an inconsistency; the 0 was `head`'s
  exit code from a pipe, not warden's. Caught it before telling the user, but only
  because the claim was re-checked in isolation.
- **Trusted stale memory over the repo.** Recalled notes asserted briefkasten did
  not use warden, while `.warden.yaml` was sitting in the project root and the
  binary was installed. The contradiction was flagged by the memory system itself
  and still nearly shaped the answer.
- **Left provenance behind on a release.** v0.20.0's release commit carries no
  warden note, because the PR branch had to be updated with main before merging,
  so the squash tree matched no locally gated commit. Not discovered until after
  the tag was pushed.

## Open Questions
- Should `checkMaildirConfinement` relax from strict startup-subtree to
  parent-directory scope? Strict refuses `/var/mail/alice` → `/var/mail/bob`;
  profiles are the sanctioned workaround, but that may prove awkward in practice.
- Does the field-level patch arm of `config.set` still earn its keep now that
  profiles cover the safe cases? Removing it would delete a whole class of guard
  logic.
- Should the Homebrew tap token be promoted to an org-level secret and the two
  naming conventions unified across klarlabs repos?
- Is `felixgeelhaar/roady`'s `HOMEBREW_TAP_TOKEN` orphaned (no release workflow
  exists there) and safe to delete?
